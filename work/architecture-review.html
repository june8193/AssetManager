Collapse Snapshot & Transaction Calculation into Deep SnapshotEngine

Strong in-process
• src/backend/routers/db_manage.py (51KB)
• src/backend/services/dashboard_service.py
Before — Shallow Router & Leaky Seam
db_manage.py (Router - 1285 lines)
  • Inline ORM queries & explicit SQL
  • Snapshot valuation & cash math inside endpoint
  • Directly instantiates DashboardService & PriceService
  • Leaks transaction logic & FX conversions
After — Deep SnapshotEngine Seam
SnapshotEngine (Deep Module)
Interface: preview_snapshot(date, fx) | commit_snapshot(previews)
Absorbs ORM queries, cash calculation, brokerage/bank valuations, & transaction pair matching.
db_manage.py (Router) shrinks to 2-line pass-through adapter

Problem

The HTTP router db_manage.py is a 51KB shallow interface containing raw ORM queries, snapshot valuation algorithms, and cash calculation logic, forcing tests to boot FastAPI HTTP TestClient.

Solution

Extract a deep SnapshotEngine module with a small interface (preview_snapshot, commit_snapshot) that absorbs all snapshot calculation, transaction matching, and DB session management.

Wins

  • ✓locality: Snapshot & cash calculation rules concentrate in one module
  • ✓leverage: One interface used by HTTP Router, CLI, and Background Tasks
  • ✓interface shrinks: Router shrinks from 1285 lines to clean thin handlers
  • ✓testability: Direct unit tests for SnapshotEngine without HTTP client setup

Problem

is_us_market_open and is_kr_market_open are duplicated verbatim across PriceService and DashboardService. Both modules instantiate Kiwoom API clients directly and manage price caching, leading to shallow wrapper leakage.

Solution

Establish a single deep MarketDataModule. Hide Kiwoom API and yfinance as internal adapters behind a unified interface (get_prices(tickers), is_market_open(market)).

Wins

  • ✓locality: Deletes duplicated market open and holiday logic across services
  • ✓leverage: Callers do not know whether a ticker comes from Kiwoom or yfinance
  • ✓real seam: Two adapters (Kiwoom, yfinance) + In-memory Fake for tests
  • ✓implementation absorbs wrappers: Cache & rate-limiting logic hidden inside module
Candidate 03

Deep Portfolio Valuation & Performance Calculation Engine

Worth exploring in-process
• src/backend/services/dashboard_service.py (35KB)
• src/backend/services/performance_service.py
• src/backend/services/ratio_service.py

Problem

Holding valuation, asset classification, FX conversion, and ROI calculations are scattered across DashboardService, PerformanceService, and RatioService. Callers must invoke multiple services and manually stitch risk metrics.

Solution

Consolidate valuation into a deep PortfolioValuator module. A single call evaluate_portfolio(as_of_date) computes holdings, valuations, asset category ratios, and risk metrics (Sharpe/Sortino/MDD) atomically.

Wins

  • ✓locality: All valuation rules, FX conversions, and ROI metrics in one place
  • ✓leverage: Single interface serves Dashboard UI, Reports, and MCP Tools
  • ✓deletion test: Collapses 3 shallow service files into 1 deep domain module
Candidate 04

Encapsulate MCP Backend Client & Tool Seam Adapter

Worth exploring local-substitutable
• src/mcp/client.py
• src/mcp/tools/assets.py
• src/mcp/tools/market.py

Problem

MCP tool modules (assets.py, market.py) perform fine-grained HTTP REST stitching (e.g. _append_performance_metrics making separate REST calls to merge Sharpe/MDD metrics), leaking backend route structures into MCP tool code.

Solution

Create a deep McpBackendAdapter seam. MCP tools interact with domain-level adapter methods rather than stitching raw HTTP endpoints and mutating unstructured JSON dicts.

Wins

  • ✓locality: REST payload stitching and error fallbacks hidden behind seam
  • ✓interface shrinks: MCP tools become thin declaration wrappers over domain adapter
Top Recommendation

Candidate 01: Deepen Snapshot Engine & Refactor db_manage.py

db_manage.py (51KB) is the single biggest source of architectural friction in the codebase. By extracting SnapshotEngine, we eliminate 800+ lines of procedural SQL/ORM code from the HTTP router, isolate snapshot valuation rules into a deep module with high locality, and enable direct fast unit testing without spinning up FastAPI HTTP servers.
